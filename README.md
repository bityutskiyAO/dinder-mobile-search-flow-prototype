# ПРОТОТИП — мобильный совместный выбор

## Результат

Прототип сохраняется в репозитории как проверяемый артефакт продуктового решения. В нём остаются четыре сравнимых варианта A–D, все контрольные состояния сквозного мобильного пути и интерактивные переходы между ними. Основным направлением для дальнейшего проектирования выбран вариант D «Гибрид»; код прототипа не является production-реализацией и должен быть переписан при разработке приложения.

Исходный тикет: [«Прототипировать мобильный путь совместного поиска»](https://github.com/bityutskiyAO/dinder-app/issues/8).

Состав артефакта:

| Файл | Назначение |
| --- | --- |
| `index.html` | Минимальная HTML-оболочка прототипа. |
| `styles.css` | Визуальные системы вариантов A–D и мобильная компоновка. |
| `app.js` | Состояния, роли, переходы и интерактивные имитации без сервера. |
| `README.md` | Быстрый запуск, описание вариантов, каталог кейсов и принятые выводы. |

## Быстрый запуск

Онлайн-версия: <https://bityutskiyAO.github.io/dinder-mobile-search-flow-prototype/?variant=D&scene=home&role=host&identity=guest>.

Для локального запуска требуется только Python 3. Из корня этого репозитория выполнить:

```sh
python3 -m http.server 4173
```

Основной кандидат:

<http://localhost:4173/?variant=D&scene=home&role=host&identity=guest>

Полезные прямые ссылки:

- [настройка организатором](http://localhost:4173/?variant=D&scene=configuring&role=host&identity=guest);
- [ожидание участником](http://localhost:4173/?variant=D&scene=configuring&role=participant&identity=guest);
- [активная оценка](http://localhost:4173/?variant=D&scene=voting&role=participant&identity=user);
- [время этапа вышло](http://localhost:4173/?variant=D&scene=expired&role=participant&identity=user);
- [гостевой профиль](http://localhost:4173/?variant=D&scene=profile&role=participant&identity=guest);
- [профиль пользователя](http://localhost:4173/?variant=D&scene=profile&role=participant&identity=user).

Параметры URL:

- `variant=A|B|C|D` выбирает вариант интерфейса;
- `scene=<id>` открывает контрольное состояние;
- `role=host|participant` переключает точку зрения организатора и участника;
- `identity=guest|user` переключает гостевой и авторизованный профиль в D.

Верхний селект переключает состояния, кнопка рядом — роль. Нижняя плавающая панель и клавиши `←`/`→` меняют вариант. Все действия выполняются только в памяти вкладки; сеть, OAuth, база данных и внешние карты не вызываются.

## Вопрос прототипа

Каким должен быть сквозной мобильный путь: от главной страницы, создания совместного выбора или входа по коду до ожидания группы, оценок заведений, таймера, найденного совпадения, решения организатора, истории и результата без совпадения? Отдельно проверяются загрузка, разрыв связи и пустые состояния.

Это одноразовый прототип без сервера и сохранения данных. Его выводы должны стать входом для продуктово-технической спецификации, а код нельзя переносить в production без нормальной реализации и тестов.

## Язык интерфейса

Интерфейс полностью русский. Английские канонические термины остаются в доменной модели и внутреннем коде, но не показываются человеку.

| Канонический термин | Текст в интерфейсе | Почему |
| --- | --- | --- |
| `User` | пользователь | Зарегистрированный человек; уточнение обычно не требуется на экране. |
| `Guest User` | гость | Коротко объясняет временный вход без регистрации. |
| `Search Session` | совместный выбор | Описывает цель процесса, а не его техническую форму. |
| `Search History` | история выборов | Связывает раздел с завершёнными совместными выборами. |
| `Host` | организатор | Показывает ответственность без оттенка администрирования. |
| `Participant` | участник | Нейтральное и привычное название члена группы. |
| `Eligible Participant` | голосующий участник | Используется только там, где важно право голоса. |
| `Place` | заведение | Естественное общее название ресторана или бара. |
| `Cuisine` | кухня | Привычное название фильтра. |
| `Dish Type` | тип блюд | Отделяет формат еды от кухни региона. |
| `Price Segment` | ценовая категория | Понятнее внутреннего слова «сегмент». |
| `Vote` | оценка | Подходит действиям «Хочу» и «Не подходит», не обещая выбор одного победителя. |
| `Round` | этап | Отдельная часть последовательной оценки заведений. |
| `Final Round` | финальный выбор | Передаёт, что участник выбирает один вариант из короткого списка. |
| `Match` | совпадение | Общий вариант, поддержанный группой. |
| `No Match` | совпадение не найдено | Понятный результат без технического кода состояния. |
| `Metro` | метро | Русское написание пользовательского фильтра. |
| `configuring` | настройка | Этап выбора фильтров и ожидания группы. |
| `round_active` | идёт оценка | Описывает доступное действие, а не внутреннее состояние. |
| `round_expired` | время этапа вышло | Объясняет причину остановки оценок. |
| `match_found` | совпадение найдено | Готовит пользователя к решению организатора. |
| `completed` | завершено | Человекочитаемый статус истории. |
| `cancelled` | отменено | Человекочитаемый статус истории. |
| `abandoned` | завершено из-за бездействия | Объясняет причину автоматического завершения. |
| `offline` | нет связи | Наблюдаемая проблема вместо технического режима. |
| `pending` | ждёт подтверждения | Объясняет неопределённый результат действия. |
| `snapshot` | актуальное состояние | Описывает загружаемые данные без протокольного термина. |
| `command_id` | тот же запрос | Передаёт безопасный повтор без раскрытия реализации. |

Названия Яндекс ID, Google и DINDER сохраняются как имена продуктов и бренда.

## Общее устройство

Во всех вариантах доступны одиннадцать общих контрольных состояний и переключение точки зрения организатора/участника. В D добавлены шесть детализирующих состояний: группа, фильтры, общие параметры, детали заведения, возврат участника и профиль. Это позволяет сравнивать базовую информационную архитектуру A–C и отдельно проверить согласованное направление D.

Переключатель состояния сверху является инструментом прототипа. Нижний переключатель A/B/C/D меняет только представление, сохраняя выбранное состояние. Стрелки клавиатуры также меняют варианты.

## Согласованное направление

Основной кандидат — вариант D «Гибрид»:

- каркас и постоянное состояние берутся из B;
- одно главное действие на текущем экране — из A;
- события группы берутся из C, но становятся компактным вторичным блоком;
- до старта события показывают вход и выход участников, изменение настроек и ход проверки данных;
- после автоматического старта блок событий полностью исчезает и не конкурирует с оценкой заведения;
- «гость» в доменной модели остаётся типом identity, поэтому приглашённая роль в интерфейсе называется «участник».

Дополнительные сценарии D:

- организатор просматривает состав группы, задаёт фильтры и общие параметры;
- участник явно видит организатора и группу, ждёт старта, выходит на главную и возвращается в активный выбор без потери прогресса;
- любой человек открывает профиль из шапки, преобразует гостевой профиль во вход через Яндекс ID, выходит на устройстве или запускает подтверждение удаления;
- успешная проверка заведений автоматически запускает первый этап и таймер;
- нажатие на карточку заведения открывает фотографии, полное описание, адрес и карту;
- фотографии переключаются кнопками или горизонтальным свайпом.

### Вариант A — «Один фокус»

**Основная идея.** На экране есть одна главная задача: создать выбор, ввести код, дождаться группы, оценить заведение или принять решение. Второстепенная информация уходит в короткие подписи и небольшие показатели.

**Информационная иерархия.** Сначала пользователь видит крупный заголовок текущего шага, затем минимальный контекст, после него — одно основное действие или чёткую пару действий. Во время оценки фотография и сведения о заведении занимают основную часть экрана. При ошибке или пустом состоянии вместо сложной панели появляется одна причина и один следующий шаг.

**Навигационная модель.** Интерфейс ощущается как последовательность экранов. Пользователь движется вперёд по процессу и почти не управляет всей системой целиком. Прогресс показывается локально: номер заведения, номер этапа и оставшееся время.

**Сильные стороны.**

- Минимальная когнитивная нагрузка и лучший акцент на текущем действии.
- Хорошо подходит для использования одной рукой и небольшого экрана.
- Проще объяснить гостю без обучения.
- Ошибки связи и ожидание организатора невозможно спутать с доступным действием.

**Риски.**

- Состояние группы и всего совместного выбора видно слабее.
- Организатору может не хватать постоянного обзора участников, таймера и прогресса.
- Частые переходы между экранами могут скрыть причинно-следственную связь событий.

**Отличие от B.** A намеренно убирает постоянную панель состояния и не пытается быть центром управления. Он выигрывает в простоте, но проигрывает в наблюдаемости.

**Отличие от C.** A показывает настоящее действие без истории его возникновения. Он быстрее ведёт к решению, но слабее создаёт ощущение совместного процесса.

### Вариант B — «Пульт выбора»

**Основная идея.** Совместный выбор представлен как управляемый процесс. Верхняя тёмная панель постоянно показывает роль, количество участников, номер этапа и таймер. Основное содержимое состоит из карточек: требуемое действие, параметры, прогресс и пояснения.

**Информационная иерархия.** Сначала пользователь видит глобальное состояние, затем карточку самого срочного действия, после неё — дополнительные сведения. Ошибки и решения организатора выделены цветной границей, поэтому операционное событие трудно пропустить.

**Навигационная модель.** Пользователь остаётся внутри одного «пульта», а карточки меняются вместе с состоянием процесса. Интерфейс менее похож на мастер шагов и больше — на компактную рабочую панель.

**Сильные стороны.**

- Наилучшая наблюдаемость всего совместного выбора.
- Особенно полезен организатору во время ожидания группы, истечения таймера и восстановления связи.
- Хорошо объясняет, почему действие сейчас доступно или заблокировано.
- Легко расширяется дополнительными показателями без перестройки всей страницы.

**Риски.**

- Самый плотный вариант; второстепенные показатели конкурируют с главным действием.
- Для обычного участника часть постоянной информации избыточна.
- Карточная структура может восприниматься как служебная панель, а не лёгкий потребительский продукт.

**Отличие от A.** B всегда сохраняет общий контекст и потому лучше для контроля, но требует больше внимания и места.

**Отличие от C.** B организован вокруг текущих показателей, а не событий группы. Он точнее и практичнее, но эмоционально суше и хуже объясняет путь, который привёл к текущему состоянию.

### Вариант C — «История группы»

**Основная идея.** Совместный выбор показан как живая последовательность событий: кто присоединился, когда началась оценка, когда вышло время и когда найдено совпадение. Текущее действие всегда находится в закреплённой нижней панели.

**Информационная иерархия.** Фон отвечает на вопрос «что происходило в группе», нижняя панель — «что мне делать сейчас». События расположены хронологически, а действие визуально отделено как временный слой поверх истории.

**Навигационная модель.** Пользователь читает поток сверху вниз, но взаимодействует в нижней панели. При смене состояния история растёт, а форма действия заменяется. Это создаёт ощущение непрерывного совместного процесса.

**Сильные стороны.**

- Лучше остальных передаёт социальность и последовательность происходящего.
- Позволяет объяснить неожиданное состояние через предыдущие события.
- Участник видит активность группы, не раскрывая индивидуальные оценки других людей.
- Найденное совпадение ощущается как кульминация общего пути.

**Риски.**

- История быстро становится длинной и требует правил сворачивания событий.
- Большая нижняя панель перекрывает часть ленты, особенно во время оценки заведения.
- Для повторяющихся оценок хронология может создавать визуальный шум.
- Организатору сложнее быстро сравнить текущие показатели, чем в B.

**Отличие от A.** C сохраняет контекст и эмоциональную непрерывность, но медленнее считывается и занимает больше пространства.

**Отличие от B.** C объясняет процесс через события, а B — через актуальные показатели. C человечнее, B эффективнее для управления.

### Вариант D — «Гибрид»

**Основная идея.** Постоянная верхняя панель B показывает активный совместный выбор, роль, группу, этап и таймер. Центральная часть наследует принцип A: в каждый момент выделено одно главное действие. События C находятся в компактной карточке ниже и раскрываются только по запросу.

**До старта.** Организатор проходит два явных шага: фильтры заведений и общие параметры. Параллельно участники могут входить и выходить, а карточка событий показывает изменения группы и настроек. Участник видит имя организатора, весь состав группы и текущую деятельность организатора, но не получает элементы управления настройками.

**Запуск.** После команды организатора выполняется финальная проверка фотографий и доступности. Пока она идёт, блок событий показывает текущий статус. Успешное завершение не требует второй кнопки: интерфейс автоматически начинает первый этап, запускает таймер с полного интервала и убирает блок событий.

**Активный этап.** Главной остаётся карточка текущего заведения. Верхняя панель показывает число участников и личный прогресс, а таймер вынесен в отдельную контрастную область с номером этапа. События группы больше не отображаются: они нужны только для прозрачности настройки до старта.

**Время вышло.** Участник видит собственный прогресс, число оставшихся без оценки заведений и последствия обоих решений организатора. Организатор вместо личного блока получает состояние группы и явный выбор между продлением и завершением этапа.

**Профиль.** Гость видит временный профиль и может войти через Яндекс ID без потери текущих выборов, оценок и истории. Авторизованный пользователь редактирует отображаемое имя, выходит только на текущем устройстве или открывает отдельное подтверждение удаления. Выход создаёт новый гостевой профиль на устройстве, а удаление заранее объясняет влияние на активные выборы и обезличивание исторической активности.

**Детали заведения.** Нажатие на карточку открывает отдельную подробную поверхность с галереей, кухней, типом блюд, ценовой категорией, описанием, адресом, ближайшим метро и точкой на карте. Галерея поддерживает кнопки и свайп.

**Выход и возврат.** Участник может уйти на главную, не прекращая участие. На главной остаётся карточка активного совместного выбора. Возврат восстанавливает текущий этап, таймер и прогресс оценок.

**Главный риск.** Гибрид легко перегрузить. Поэтому постоянными остаются только три показателя, события ограничиваются этапом настройки, а сами настройки разделены на два шага.

## Каталог проверяемых кейсов

| Состояние | Для кого | Что проверяется | Основное действие и вывод |
| --- | --- | --- | --- |
| `home` — главная | Все | Первый вход, отсутствие обязательной авторизации, наличие активного выбора после выхода на главную. | Создать совместный выбор, войти по коду, открыть историю или вернуться в активный выбор. Активный процесс не должен теряться за главным экраном. |
| `join` — вход по коду | Участник | Вход в существующую группу без обязательного Яндекс ID. | Ввести короткий код и присоединиться. Гостевой профиль создаётся автоматически. |
| `configuring` — ожидание и настройка | Обе роли | Разные обязанности до старта. | Организатор переходит к фильтрам и параметрам; участник видит организатора, группу, текущую настройку и ждёт запуска. |
| `group` — группа и события | Обе роли, только D | Состав группы, явный организатор, вход/выход участников и события настройки. | Организатор копирует приглашение; участник может выйти на главную. События существуют только до запуска. |
| `filters` — фильтры заведений | Организатор, только D | Город, кухня, тип блюд и ценовая категория до запроса данных. | Выбрать фильтры, увидеть предварительное число заведений и перейти к общим параметрам. |
| `settings` — общие параметры | Организатор, только D | Длительность этапа, максимум заведений, вход новых участников и роль организатора. | Сохранить параметры и запустить финальную проверку данных. |
| `loading` — финальная проверка | Обе роли | Обновление фотографий и доступности перед фиксацией пула. | Показывать прогресс и статус в событиях. После успеха автоматически начать первый этап и таймер без второй кнопки. |
| `voting` — оценка | Обе роли | Оценка текущего заведения, личный прогресс и ограничение по времени. | «Хочу» или «Не подходит». Таймер вынесен в отдельный контрастный блок; события группы после старта скрыты. |
| `detail` — детали заведения | Обе роли, только D | Полное описание, несколько фотографий, адрес, метро, средний чек и расположение. | Листать фотографии кнопками или свайпом, открыть точку на карте и вернуться к оценке. |
| `returning` — возврат | Участник, только D | Возвращение после ухода на главную без потери участия. | Увидеть организатора, текущий этап, таймер и личный прогресс, затем продолжить оценку. |
| `offline` — нет связи | Обе роли | Безопасное восстановление после разрыва связи. | Объяснить статус последней оценки, загрузить актуальное состояние и повторить тот же запрос. |
| `expired` — время вышло | Обе роли | Разные данные и действия после остановки оценок. | Участник видит личный прогресс и последствия решений; организатор — сводку группы и выбор между продлением и завершением. Таймер отдельно показывает `00:00`. |
| `match` — совпадение | Обе роли | Общий вариант и исключительная ответственность организатора. | Организатор подтверждает заведение или продолжает поиск; участник ждёт решения. Совпадение не обещает бронирование. |
| `no-match` — без совпадения | Обе роли | Терминальный исход без общего варианта. | Объяснить результат, не раскрывая чужие оценки, и предложить новый совместный выбор. |
| `history` — история | Все | Завершённые выборы, срок хранения и приватность оценок. | Показывать фиксированные параметры, роль, участников, итоговое заведение и только собственные оценки. |
| `empty` — пустая история | Все | Понятное пустое состояние без служебной терминологии. | Предложить начать первый совместный выбор. |
| `profile` — профиль | Гость и пользователь, только D | Авторизация, изменение имени, выход и удаление профиля. | Гость входит через Яндекс ID с сохранением данных. Пользователь выходит на устройстве или подтверждает необратимое удаление после просмотра последствий. |

## Ролевые различия в D

| Область | Организатор | Участник |
| --- | --- | --- |
| Подготовка | Настраивает фильтры и общие параметры, запускает проверку. | Видит организатора, состав группы, события и текущий статус подготовки. |
| Группа | Копирует приглашение и управляет процессом. | Может уйти на главную и затем вернуться в тот же активный выбор. |
| Оценка | Голосует на тех же условиях, что остальные. | Голосует независимо; чужие оценки не видит. |
| Время вышло | Видит состояние группы, продлевает или завершает этап. | Видит только личный прогресс и последствия решения организатора. |
| Совпадение | Подтверждает заведение или продолжает поиск. | Ждёт решения и не получает управляющих действий. |
| Профиль | Идентичен профилю любого пользователя; роль в группе не даёт дополнительных прав над identity. | Идентичен профилю организатора. |

## Финальные выводы по варианту D

1. **D становится базовым направлением.** Он сочетает постоянный контекст B, одно главное действие A и социальные события C без превращения интерфейса в ленту.
2. **События нужны только во время `configuring`.** Они показывают присоединение и выход участников, изменение настроек и финальную проверку. После автоматического старта блок исчезает во всех активных и терминальных состояниях.
3. **Верхняя часть экрана отвечает за ориентацию.** Она показывает активный совместный выбор, роль, группу и личный прогресс. Таймер не является третьей равнозначной метрикой: во время этапа он вынесен в отдельную заметную область и начинается с согласованных 5 минут по умолчанию.
4. **Подготовка организатора разбита на понятные шаги.** Сначала фильтры запроса заведений, затем общие параметры, после них — финальная проверка данных.
5. **Старт после успешной проверки автоматический.** Отдельное подтверждение не требуется; первый этап и таймер начинаются одновременно.
6. **Основной объект активного этапа — текущее заведение.** Карточка ведёт в детали с галереей, описанием и расположением. Карта ограничена одной точкой в деталях и не превращается в отдельный сценарий поиска по карте.
7. **Истёкший этап объясняет последствия, а не только числа.** Участник видит свой незавершённый объём и два возможных исхода; организатор получает данные, необходимые для решения.
8. **Уход с экрана не равен выходу из группы.** Участник возвращается в активный выбор с теми же прогрессом и таймером.
9. **Профиль доступен из любого основного экрана.** Первый вход через Яндекс ID преобразует гостевой профиль в постоянный без переноса истории в новую identity. Выход и удаление разведены как разные действия.
10. **Пользовательский язык отделён от доменной модели.** В UI используются «совместный выбор», «организатор», «участник», «заведение», «оценка» и «этап»; канонические английские термины остаются во внутренних контрактах.

## Что прототип намеренно не решает

- финальную визуальную систему, бренд, анимации и production-компоненты;
- реальный OAuth, серверные сессии, WebSocket, повтор запросов и хранение данных;
- окончательный картографический провайдер, тариф и политику тайлов;
- реальные фотографии и правила их загрузки из каталога;
- точную адаптацию для всех размеров экранов и полный аудит доступности;
- аналитику, защиту от злоупотреблений и эксплуатационную наблюдаемость.

### Карта в деталях заведения

Прототип использует локальный макет карты, чтобы не закреплять инфраструктурный выбор. Для реализации подходит Leaflet с тайловым слоем OpenStreetMap: контейнеру задаётся явная высота, карта получает marker с доступным названием, а слой — обязательную атрибуцию OpenStreetMap. В production также нужно отдельно выбрать tile-provider и проверить его политику использования; публичный tile-сервер OpenStreetMap нельзя считать безусловным production-бэкендом.
